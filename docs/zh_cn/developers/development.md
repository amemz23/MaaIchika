# 开发手册

环境搭建、工具链、架构约定。硬性规范见仓库根目录 [AGENTS.md](../../../AGENTS.md)，
每个模板实测出来的分数基线见 [识别基线](./recognition-baseline.md)。

## 1. 技术栈

纯 Pipeline JSON 项目，没有自定义 agent。

| 项         | 取值                                                          |
| ---------- | ------------------------------------------------------------- |
| 运行时     | [MaaFramework](https://github.com/MaaXYZ/MaaFramework) v5.16+ |
| 接口协议   | Project Interface **V2**（`interface_version: 2`）            |
| 控制器     | `Adb`，`display_short_side: 720`                              |
| 坐标基准   | **1280×720**                                                  |
| 无头运行   | `@maaxyz/maa-node` 5.16.x（`tools/run.mjs`）                  |
| 图形客户端 | [MXU](https://github.com/MistEO/MXU)（可选，给人用）          |

## 2. 环境

### 2.1 依赖

```bash
# Python：截图/裁剪/校验/打包脚本用（需要 Pillow）
pip install pillow

# Node 依赖：maa-node（无头运行）、maa-tools（加载校验）、prettier
npm install          # 或 pnpm install

# OCR 模型（约 30MB，不入库）
python tools/fetch_ocr.py
```

> **OCR 模型没装时，OCR 节点会静默不命中** —— 表现是"任务跑完了但什么都没做"，
> 和节点写错极难区分。第一次跑之前务必确认 `assets/resource/model/ocr/` 里三个文件都在。

### 2.2 设备

设备必须是 **16:9**。MaaFramework 只按 `display_short_side` 等比缩放，不补偿宽高比：
2560×1440 会缩成 1280×720（正好是坐标基准），而 2400×3392 的平板会缩成 1018×720，
坐标和模板一起失效。

```bash
python tools/device.py info     # 看当前分辨率/宽高比
python tools/device.py fix      # 刷成 16:9（竖屏原生平板 → 1440x2560@420）
python tools/device.py check    # 跑任务前自检：比例 / 画布 / 方向
python tools/device.py reset    # 用完还原物理分辨率
```

`wm size` 是临时覆盖，重启设备即失效。**竖屏原生设备要写竖着的宽高**（`1440x2560`），
写反了横屏游戏会被强制竖屏 —— 这一点 `device.py fix` 会自动判断并交换，手填时要小心。

### 2.3 两种跑法

**A. 无头运行（开发用，推荐）**

```bash
node tools/run.mjs 任务_启动              # 跑一个任务入口
node tools/run.mjs 任务_领礼包 任务_演出一场   # 一次连接跑多个
node tools/run.mjs --list                 # 列出所有节点
```

它会打印每个节点的识别结果（命中/未命中、box、score、OCR 文本），并把识别可视化图
落到 `debug/`。判定标准是三种：

| 结果           | 含义                                                       |
| -------------- | ---------------------------------------------------------- |
| 完成（已验证） | 节点链落在 `公共_主页锚点` / `完成_*` 上                   |
| 结束但未验证   | 流程走完了，但没到验证型终点 —— **等于没做成，要当失败看** |
| 失败           | Maa 报失败                                                 |

**B. MXU（给别人用）**

```bash
python tools/pack.py                 # assets -> install/
# 把 mxu.exe 放进 install/，MaaFramework 的 bin/*.dll 与 share/MaaAgentBinary 放进 install/maafw/
# 以管理员身份运行 install/mxu.exe
```

MXU 是单实例程序，已经在托盘里时再双击会直接退出（看起来像"闪一下没了"）。
改了 pipeline 后要**完全退出 MXU 再重开**，点"重新加载"不清模板缓存。

## 4. 架构：状态机 + 验证型终止

### 4.1 为什么不是"一条直线"

MaaFramework 的 `next` 是**候选列表**：按顺序识别，命中第一个就执行它，然后走它自己的
`next`。于是有两种典型坏味道：

1. 把辅助节点（等加载、关弹窗）直接写进 `next` → 命中后走完它的 `next` 就结束，
   主流程被吞掉。
2. 每步都是"点一下 → 下一步"，只要有一次点击丢了，整条链就在"等一个不会出现的画面"
   中耗到超时，最后**静默成功**结束。

本项目用三条约定解决：

- **辅助节点一律 `[JumpBack]` 引用 + `max_hit`**：做完回父节点重新判断。
- **导航节点把自己放进 `next`**：点击丢了下一轮重点，点成功了画面就变了、自然不再命中。
- **终点必须是验证型节点**（`公共_主页锚点`）：用"主页底部导航真的出现了"来证明任务做成。

### 4.2 节点分工

| 前缀     | 作用                                  | 例                                                             |
| -------- | ------------------------------------- | -------------------------------------------------------------- |
| `公共_`  | 任意界面可复用的辅助/状态             | `公共_等待加载`、`公共_关公告`、`公共_回主页`、`公共_主页锚点` |
| `任务_`  | 任务入口，`interface.json` 的 `entry` | `任务_启动`、`任务_领礼包`、`任务_演出一场`                    |
| 界面动作 | 具体界面的一个动作                    | `主页_进礼物箱`、`演出_开演`                                   |

### 4.3 公共节点

| 节点                 | 识别                                | 动作                                   | 说明                                                   |
| -------------------- | ----------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| `公共_等待加载`      | 右下角初音头像（模板）              | DoNothing                              | `[JumpBack]` 回父节点轮询，等它消失                    |
| `公共_关公告`        | 面板右上角 X（模板 0.72）           | Click                                  | 同一 X 在不同面板上分数不同，阈值实测 0.787 起         |
| `公共_Google登录`    | OCR「使用 Google 账号登录」         | ClickKey BACK                          | 系统级 sheet，按返回键就过                             |
| `公共_回主页`        | 左上角返回箭头**字形**（模板 0.80） | Click                                  | 自循环 + `max_hit 8`                                   |
| `公共_主页锚点`      | 底部导航「ガチャ」                  | DoNothing                              | 验证型终止节点                                         |
| `公共_卡死_重启游戏` | DirectHit（上一步已证明画面死了）   | Shell `am force-stop com.sega.pjsekai` | **只能从卡死检测节点进来**，挂正常流程里会白丢一场演出 |
| `公共_卡死_启动游戏` | DirectHit                           | StartApp                               | 冷启动 → 标题页 → 主页锚点（恢复完仍是"已验证"）       |
| `公共_失败`          | DirectHit                           | StopTask                               | 让失败在日志里看得见                                   |

### 4.4 任务链

| 任务            | 链                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| `任务_启动`     | StartApp → 标题页点击 → 主页锚点                                                                                |
| `任务_领礼包`   | 主页 → 礼物箱 →（空：直接返回 / 有：一键领取 → 结算 OK 循环）→ 返回 → 主页锚点                                  |
| `任务_回主页`   | 清弹窗/等加载 → 连点返回箭头 → 主页锚点                                                                         |
| `任务_进演出`   | 主页 → LIVE → 单人 → 决定，停在编成页（不消耗 Live Bonus）                                                      |
| `任务_收尾结算` | LIVE CLEAR → 逐页 次へ/OK → 回 LIVE 菜单 → 回主页                                                               |
| `任务_演出一场` | 主页 → LIVE → 单人 → 决定 → 打开 AUTO → 开演 → 等结束 → 逐页结算 → 回主页                                       |
| `任务_过剧情`   | 主页 → 故事 TOP → 主/活动卡 → 決定 → 选未读章节 → 语音弹窗（勾连读 + ボイスなし）→ 纯点击推进 →（没有未读就停） |

## 5. 写节点的流程

1. **截图**：`python tools/device.py shot scratch/home.png`（同时存一份 raw）
2. **裁模板**：在 `tools/crops.json` 里登记 `{name, src, box, out, note}`，
   跑 `python tools/crop.py --sheet`，看 `scratch/sheet.png` 确认裁得对
3. **写节点**：先填 `threshold: 0.8`
4. **量阈值**：
    ```bash
    node tools/score.mjs --dir scratch/shots      # 给所有截图打分
    python tools/analyze_scores.py                # 按 tools/labels.json 的标签算正负样本
    python tools/analyze_scores.py --apply        # 把建议阈值写回 pipeline
    ```
    `gap = 正样本最低分 - 负样本最高分`，**gap < 0.1 就该换模板或换识别方式**，
    而不是硬压阈值。
5. **真机跑**：`node tools/run.mjs 任务_xxx`，看识别分数和节点链
6. **自检**：`python tools/check_json.py` + `npm run check:maa` + `npm run format:check`

## 6. 踩过的坑（都是真机撞出来的）

### 6.1 主页左上角那个圆形按钮不是返回键

左上角有个白色圆形的「世界/区域」按钮，形状和返回箭头几乎一样。用带圆底的截图当模板，
在主页上会拿到 0.959 —— 于是"回主页"把区域菜单点开了。

**解法**：模板只裁**箭头字形**，不带白色圆底。改完主页上是 0.515、真箭头上是 1.000。

### 6.2 半透明/带特效的锚点会骗人

「演出中」想用右下角 `AUTO LIVE` 胶囊当锚点，结果演出特效会盖住它 —— 实测最低只有 0.41，
会在半场就误判"打完了"。

**解法**：不认"进行中"，只认"结束信号"（LIVE CLEAR 的 OCR / 结算按钮的 OCR），
中间整段用 `DirectHit + DoNothing` 空转等待。

### 6.3 从旧项目抄来的 HSV 色带会永远命中

旧项目的加载页是"中间一条深紫横带"，`ColorMatch(HSV, count: 120000)` 很好用。
但换到现版本，同一套数值在标题页和主页上都能满命中 —— 于是"等待加载"变成永远成立，
整条链卡在等待里。

**解法**：`node tools/probe.mjs <截图> <参数>` 一测就知道。加载锚点改成认
右下角初音头像的模板。

### 6.3.1 Google 登录弹窗：`ClickKey` 会直接**动作失败**

那个「使用 Google 账号登录」的弹窗是 `com.google.android.gms` 的 `ConsentActivity` ——
**独立系统 Activity、受保护窗口**。识别没问题（OCR 0.997），但 `ClickKey(BACK)`
实测返回**动作失败**：注入的按键到不了那个窗口。动作失败且 `on_error` 为空时，
框架不会回跳，于是整条启动链在 17 秒内"失败退出"。

**解法**：改用 `Shell` 动作跑原始 adb：

```json
"action": { "type": "Shell", "param": { "cmd": "input keyevent 4" } }
```

### 6.3.2 验证型终止节点绝对不能写成 `[JumpBack]`

`公共_主页锚点` 是"永远命中"的终止节点。一旦写成 `"[JumpBack]公共_主页锚点"`，
它在父节点的 next 里就是：命中 → 执行 → 回跳 → 父节点重扫 → 又命中 → 无限空转，
直到父节点超时失败。**终点节点只能直接引用。**

### 6.4 点击丢了会卡死整条链

刚 `StartApp` 拉起游戏时，画面可能还是上一次的残像；这时候点标题页是点不动的，
而"标题页还在 → 是不是要点一下"这种判断不会自动重来。

**解法**：导航节点的 `next` 里放上**它自己**。点成功了画面变，它自然不再命中；
点丢了下一轮继续点。配 `max_hit` 当出口。

### 6.5 `timeout` 挂错地方

`timeout` 是**本节点 next 列表**的识别窗口。想等某个画面出现，要加在**它的前一个节点**上；
加在自己身上只会让自己更早失败。

反过来说：**没有锚点的过渡画面只能靠父节点的 timeout 兜**。标题页点进去之后有
「プロジェクトセカイによろこそ。」和 TIPS 两屏，目前都没做识别（不值得，一闪而过），
所以 `标题_点击开始` 的 timeout 放到 180s，让它一直等到主页锚点出现。
timeout 给太短的表现就是"偶尔启动失败、偶尔又好了"。

### 6.5.1 开演前必须验证 AUTO 真的开了

编成页的 AUTO 开关被点丢时，游戏照样开演 —— 结果是整场 0 分、LIVE 结算没有奖励。
所以流程是「认 OFF 态 → 点击 → **认 ON 态确认** → 才允许点开演」：

| 模板                | OFF 画面 | ON 画面          |
| ------------------- | -------- | ---------------- |
| `live/auto_off.png` | 1.000    | 不命中（0 结果） |
| `live/auto_on.png`  | 0.354    | 1.000            |

这就是"动作之后必须验证结果"的价值：光有"点了"不等于"成了"。

### 6.6 别用 PowerShell 批量改 JSON

`Set-Content -Encoding UTF8` 会把中文和引号写坏。批量改文件一律用 Python 读写 UTF-8。

### 6.7 剧情画面有"三种长得完全不一样"的状态

| 画面      | 特征                                        | 锚点                                                        |
| --------- | ------------------------------------------- | ----------------------------------------------------------- |
| 对白      | 角色立绘 + 底部对白框                       | 右上角 ⋯ 圆钮（实测 0.93+）、右下角 AUTO 文字               |
| 旁白/演出 | 上下纯黑边（letterbox），⋯ 和 AUTO 都被隐藏 | 黑边本身：`ColorMatch(method 6, 0..16)` 实测 104000 px 全黑 |
| 章节列表  | 右侧竖排章节行                              | 红色未读角标（HSV H≈169、count≈288）                        |

只用 ⋯ 当锚点，会在旁白画面直接断链 —— 演出现场就是被这个咬到的。

### 6.7.1 热循环里不要挂 OCR 候选

故事\_连点 这种「每秒跑一轮」的节点，
ext 每多一个候选就多一次识别。实测在它的 next 里
挂 5 个通用处理节点（其中 2 个是 OCR）后，单轮点击从 ~0.8s 变成 ~3s —— 一集剧情从 15 分钟变成
1 小时。**昂贵识别（OCR）只挂在低频节点上**（剧情入口、界面切换处），热循环只留便宜的模板匹配
和最必要的出口。

### 6.8 剧情一旦开始就没法退出

返回键、点画面，全都只是"推进对白"；⋯ 菜单里只有 しおり/オート/連続再生/スキップ/早送り/
非表示/ログ，**没有退出项**。这是游戏机制，不是识别问题。所以：

- 别在剧情播放时启动别的任务（`公共_回主页` 在剧情里按返回只会推进剧情）；
- 自动读剧情的入口必须从主页开始，读完之后自己回主页；
- 调试剧情链时留一个 `node tools/device.py` 终端在旁边，方便手动干预。

### 6.9 「画面死了」不要靠长 timeout 干等

标题页点不动、演出 420 秒还没结束信号，本质都是**同一件事：截图不再变化**。纯 Pipeline 只能等
timeout 然后盲点一下屏幕判失败；`ScreenFrozen`（`agent/custom.mjs` 的 Custom 识别）能当场认出来，
改成「杀进程 → 冷启动 → 重走启动链」，恢复完照样落在 `公共_主页锚点` 上。

写这类节点必须记住四条（都是真机撞出来的，详见 [agent-plan](./agent-plan.md)）：

1. **只挂 `on_error`，不能进 `next`**。启动过程里「プロジェクトセカイによろこばせ。」和 TIPS
   两屏本来就是静态画面，进 `next` 会把正常启动误判成卡死、重启掉。
2. **`on_error` 里它必须是唯一候选**。同一轮候选按顺序识别，DirectHit 永远命中 →
   `on_error = ["卡死检测", "DirectHit"]` 会让卡死检测永远只有 1 次采样机会、攒不够帧。
   要把老的兜底（`演出_点屏幕`）挪到卡死节点**自己的** `on_error` 里。
3. **`on_error` 有它自己的整个 timeout 窗口**（用父节点的 `timeout` / `rate_limit` 反复轮询）。
   所以 `times: 3` 在父节点 `rate_limit: 800~900ms` 下约 2.4~2.7 秒就能命中；
   卡死节点自己的 `timeout` 决定"多久没命中就放弃走兜底"。
4. **代价要说清**：冷启动意味着那场演出 / 那个界面丢了。`tools/run.mjs` 会在节点链出现
   `公共_卡死_*` 时多打一行 `[warn]` —— 因为链尾仍然可能是"完成（已验证）"，光看结论看不出来。

验证方法：把设备停在**静态画面**（系统设置页）上跑 `node tools/run.mjs 标题_点击开始`，
期望 15 秒超时后 `标题_画面卡死` 命中 → 冷启动 → 主页锚点。动态画面（游戏主页）上则不应命中。

### 6.10 同一个按钮「可点 / 不可点」，OCR 分不出来

任务页右下角的「一括受け取り」在**没有可领奖励时仍然是那颗按钮**，只是从白底变灰底：

| 按钮态                  | 实测颜色      | `roi [1040,640,200,52]` 里的 count |
| ----------------------- | ------------- | ---------------------------------- |
| 白（可点）              | (255,255,255) | 4975 ~ 5149                        |
| 灰（已领完 / 点不动）   | (127,127,144) | 5470 ~ 5501                        |
| 青绿主按钮（次へ / OK） | (119,238,221) | 9567 ~ 9589                        |

老代码的注释里写着"灰按钮 OCR 照样命中、点了没反应、轮询空转，所以暂时只接一个 tab"——
就是这个差异。**纯色填充块用 TemplateMatch 打分没有意义**（CCOEFF 对常数模板不稳定），
这类「颜色状态」要交给 `ColorMatch` 的 `count`。

写法约定：

- **「能不能点」= `And(白底颜色, OCR 文字)`**：单看颜色会被纯白加载页骗（welcome/loading 页
  白色像素 6400+），单看 OCR 认不出灰态。
- **「这一页有没有主按钮」= 青绿颜色单独就够**：结算页 9567，同一块区域在演出过程中
  只有 0~274（那是 AUTO LIVE 胶囊）、加载页 834 —— 阈值 3000 两边都有 2~3 倍余量。
- **OCR 留作兜底**：`Or(青绿颜色, OCR)` 里青绿先命中时不跑 OCR，正好省一次全宽文字识别。
- 青绿这组在**活动列表页**（`st03/st04`）也有 9394 —— 那不是误判，那是**同一颗青绿主按钮**；
  它只是不出现在结算上下文里，所以不影响。
- `tools/check_params.py` 现在连 Or/And 里内联的 `ColorMatch` 也查通道数和 `lower <= upper`
  （写错就是静默永不命中，和模板路径写错一样难查）。

**参数只写一份：识别片段节点。** 上面三种按钮态各对应 `08_按钮.json` 里的一个节点
（`公共_按钮_青绿主按钮` / `公共_按钮_白底可点` / `公共_按钮_灰底已领完`），它们动作是
`DoNothing`、`next` 为空，**只被 `Or`/`And` 用节点名引用**（MaaFramework v5.7+）：

```jsonc
{ "recognition": { "type": "Or",  "param": { "any_of": ["公共_按钮_青绿主按钮", { /* 内联 OCR */ }] } } }
{ "recognition": { "type": "And", "param": { "all_of": ["公共_按钮_白底可点",   { /* 内联 OCR */ }] } } }
```

已在 5.16 上实测可用（`Or` 单引用、`And` 片段+内联混写都验过），`tools/audit.py` 也认这种节点：
被 `any_of`/`all_of`/`color_filter` 按名字引用过的节点算「识别片段」，不套用「next 为空必须是
验证型终止节点」那条规则。改颜色只需要改一个地方。

### 6.11 「阈值偏低」和「写死坐标」各咬了一口（同一天连撞三个）

三个都是"离线看着没问题、真机一次就翻车"的，记下来省得再犯：

| 现象                                                     | 根因                                                                                                                                                                           | 修法                                                                                              |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 演出在 **AUTO 没开**的状态下开演，整场 0 分、LIVE FAILED | `演出_选曲确认` 阈值写成了 0.67：在**编成页**上它把右侧圆形**播放按钮**误认成「決定」拿到 0.779 就点了下去 —— 等于绕过"验证 AUTO 才开演"这条硬规矩                             | 阈值提到 **0.90**（同一模板正样本实测 0.999~1.000）；`清火_选曲` 同模板同坑，一起改               |
| 挑战场 AUTO 开关拨不动                                   | `演出_打开AUTO` 的 TouchDown 写死 (530,665)，但挑战场开关比单人场大一圈、整体偏右约 47px（单人场框 `[522,642,122,42]`、挑战场 `[569,643,122,42]`）→ 手指按在了开关左边的空白上 | 用 `anchor` + `target: true` / `target: "[Anchor]AUTO开关"`，让按下点和拖拽终点都**跟着识别框算** |
| 收尾卡在「今週のチャレンジスタンプ」浮层 48 秒后失败     | `演出_结算开场.next` 里没有 `演出_阶段面板`（`清火_循环结算开场` 有，这儿漏了）→ 浮层没有 次へ/OK，链路 polling 12 秒后落到 `on_error`                                         | next 补 `[JumpBack]演出_阶段面板`，末尾再用 `公共_点一下` 兜住没枚举到的浮层                      |

两条衍生经验：

- **Maa 在 target 矩形内是随机取点的**。所以"跟着框走"不能只写 `target_offset: [-50, 0]`：
  那个矩形本身有 122px 宽，随机落点会飘到框外、按空。要用**负的宽高把矩形夹窄** ——
  `target_offset: [8, 8, -110, -26]` 的意思是"从框左上角 +8,+8 开始，取 12×16 的一小块"。
  实测落点 `(538,655) → (620,661)`，正好是旋钮的 OFF 位拖到 ON 位。
- **改完先用 `tools/replay.mjs` 验，别急着上真机**：它会打印 TouchDown/Move/Up 的实际落点，
  也能验"某个模板会不会在别的页面上误命中"。今天就是靠它确认「编成页不再误命中播放按钮」
  「拖拽落点正确」之后才上真机的 —— 一轮回放几百毫秒，真机一场 3 分钟。

### 6.12 两个兜底节点的额度怎么给（顺带：`完成（已验证）` 会骗人）

结算链上有两个"兜底"节点，它们的 `max_hit` 不能按"大概点几次"拍脑袋：

- **`公共_点一下` 是 `DirectHit`** —— 每轮没有别的候选命中就会点一次。过场动画期间候选全都 MISS，
  于是每 300ms 烧一次额度。真机实测一条任务链里被烧光 24 次，之后链路卡到超时才失败。
  现在 `rate_limit: 800`（别在动画里空点）+ `max_hit: 60`（一条链要结算好几场，额度是按链累加的）。
- **`演出_阶段面板` 的触发次数取决于"这一天弹了多少浮层"**：新一天第一场结算实测连点 **12 次**
  （挑战印章 / 挑战段位 UP / 玩家等级 UP / 剧情解放…），原来的 `max_hit: 12` 刚好用完就卡住。
  现在 30。

**`完成（已验证）` 只证明"链尾落在主页锚点"，不证明目标达成。** 清火循环踩过：
结算半路失败 → 降级回主页 → boost 还剩 21 点时任务照样报「完成（已验证）」。
现在 `tools/run.mjs` 对 `任务_清火循环` 额外检查节点链里有没有 `公共_体力为0`，没有就打 `[warn]`。

> 经验：**凡是"有量化目标"的任务（打光体力 / 领完 N 个 tab），判据要落在那个量化证据上，
> 不能只看链尾**。链尾只证明"回到了一个好状态"。

## 8. 提交前

```bash
python tools/check_json.py        # JSON / 引用 / 占位 / 环无出口 / i18n
node tools/check_interface.mjs    # 用真实 MaaFramework 加载 interface.json + 资源包（离线）
npm run format:check              # prettier --check
node tools/run.mjs <改动涉及的入口>   # 真机，必须"完成（已验证）"
```

`check_interface.mjs` 和官方的 `maa-tools check` 检的是同一件事（把 interface.json 与资源包
喂给 MaaFramework），区别是前者用 `node_modules/@maaxyz/maa-node` 里已经装好的那份
MaaFramework、**不联网也不写工作目录外**；后者会把运行时下载到用户缓存目录。
CI 里两个都跑，但 `maa-tools` 那条是 `continue-on-error`。

> **重复路由**（官方报 `重复路由 X`）有两种：同一个节点同时出现在 `next` 和 `on_error`；
> 或同一个列表里写了两次。修法是保留正常路径、删掉 `on_error` 里的重复项，列表内去重。
> 这一轮就是靠 `maa-tools check` 才发现 —— 之前 5 个任务入口都带着这个错。
> 现在 `check_json.py` 也有同样的离线检查（`check_dup_routes`），不联网也拦得住。

> 另一个从 `maa-tools check` 学到的点：**验证型节点要放在 `next` 里，补救动作放 `on_error`**。
> `演出_确认AUTO` 原来 `next` 里直接放着 `演出_开演`，等于「AUTO 没确认成功也照样开演」，
> 验证形同虚设。改成 `next = [演出_开演]` / `on_error = [演出_打开AUTO]` 之后才真的"验证通过才开演"。
